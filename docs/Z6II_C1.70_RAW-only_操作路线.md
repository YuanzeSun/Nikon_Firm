# Nikon Z6 II C1.70 仅 HDMI RAW 解锁：操作路线与复核记录

本文对应仓库中的 `firmware/Z6II_C1.70_RAW_only/Z6_2_0170.bin`。它只处理 HDMI RAW 能力判断，**不修改 120 分钟录像功能**。

## 1. 目标和范围

原始目标包含两个方向：打开 HDMI RAW，以及把录像时长改为 120 分钟。经过拆分和复核，发布的是风险范围更小的 RAW-only 包：

- 保持机型和版本为 Nikon Z6 II C1.70。
- 只让 RAW 能力查询中的 selector `0x12` 返回可用。
- 保留原来的录像时长表、录像引擎启动检查和特殊模式限制。
- 不写入相机设置、不修改 NVRAM，不加入永久服务模式入口。

这样发布后，普通录像仍按官方默认策略运行，时长上限仍是 1,799,000 ms，即 29 分 59 秒；120 分钟修改没有放进这个文件。

## 2. 分析路线

### 2.1 文件结构

首先保留官方 C1.70 原文件的 32 字节外层头部和容器布局，解码后识别出 5 个模块。每个模块都有独立 CRC，整个容器还有尾部 CRC；外层头部还保存升级包摘要。

### 2.2 反汇编和伪代码

“反编译”在这里不是把整个固件还原成可直接编译的 C 工程，而是：

1. 用 Ghidra、Capstone 等工具识别 ARM Thumb 指令和调用关系。
2. 把相关函数整理成伪代码，确认它实际读取哪些能力字节。
3. 用 Unicorn 对原始指令和候选指令做受控模拟。
4. 只在确认功能分支后改动原始机器码，再重新计算包内校验。

相关能力判断函数位于运行地址 `0x103c3114` 附近。RAW selector `0x12` 原本读取能力区的一个字节，只有该字节等于 `0xb2` 才返回 1；不满足时跳转到返回 0。selector `0x14` 和其他 selector 仍走原逻辑。

## 3. 实际修改

唯一的指令修改如下：

```text
运行地址  : 0x103c3128
模块偏移  : 0x003a3128（以主模块运行基址 0x10020000 计算）
原指令   : 01 d1    bne  0x103c312e
修改后   : 00 bf    nop
```

这样会跳过 RAW selector `0x12` 的“能力字节不满足则返回 0”分支，随后执行原有的 `movs r0, #1; bx lr`。其他 selector、读取地址、调用约定和后续逻辑没有改动。

重新打包后：

- 解码主模块只多 2 个变化字节。
- 主模块 CRC 重新计算。
- 容器 CRC 重新计算并验证，数值恰好与原值相同。
- 外层摘要重新计算。
- 整个 BIN 与原始官方文件共差异 24 字节。
- 文件长度仍为 49,002,888 字节，版本字段仍为 C1.70。

没有重新编译“伪代码”，也没有把 Ghidra 输出当成源码回编译；发布文件是基于官方二进制的定点机器码补丁和重新封装。

## 4. 离线校验路线

构建和复核按以下顺序进行：

1. 校验官方输入文件 SHA-256，防止基准文件不是预期 C1.70。
2. 解码容器并解析 5 个模块的名称、偏移和长度。
3. 对原始数据体复现官方外层摘要；复现失败则停止构建。
4. 检查补丁位置原字节必须是 `01 d1`，只替换为 `00 bf`。
5. 检查 126 项录像时长表、录像引擎启动检查和特殊模式时长限制没有变化。
6. 重新计算主模块 CRC、容器 CRC 和外层摘要，再编码回升级文件。
7. 独立解码候选文件，逐字节确认只有预期区域变化。
8. 用原始认证指令、升级包解析路径和 RAW 选择路径做机器码模拟。

结果摘要：

```text
候选包 SHA-256       f3e4fa07de6a8818d4bbf1ef65cb3ee5b7954bee8a353fd9b65ca7b7e4e9b11e
主模块 SHA-256       9d33bd329349285b356643b72434953c2ded525330d5a60441fcc35bb5d69828
主模块变化           2 字节
完整文件变化         24 字节
RAW 路径离线用例     512 个通过（原版 256 个、候选 256 个）
升级包解析           接受候选包
录像时长策略         未改变
```

离线模拟使用替代的相机属性和 HDMI 接收端能力，不等于实测 HDMI 电气链路或外接录机兼容性。

随后再次复核了 RAW 能力字节的 256 种取值，以及其他 selector 的 5,116 组对照；其他 selector 的行为与原版一致，没有新增 RAM 写入。该测试只覆盖所列输入范围，不是全固件的证明。

### 4.1 缺失认证数据的取得和复用

外层摘要还需要运行地址 `0x10000088` 开始的 8 字节。这段不在官方升级文件所带主模块中，不能只凭升级 BIN 直接重建摘要。

当时先尝试普通诊断读取，发现通用读取路径拒绝目标 ROM 区间。随后，在用户明确允许临时维修入口后，经 USB/WPD 进入 `F001` 维修状态，备份两处 RAM，通过临时调整读取缓存路径取得该 8 字节，再恢复 RAM 并发送 `F002` 退出。日志记录恢复成功、退出成功；没有用该读取步骤写入非易失设置或刷写固件。读取脚本会临时写 RAM，不属于纯只读操作。

认证变换和摘要为：

```text
suffix = boot_bytes XOR e22b5d787c693ffe
outer_digest = SHA1(decoded_body || suffix)
```

后续离线重建先要求这些输入能精确复现官方原文件的摘要，才为修改包计算新摘要。本私有仓库已经保存读取值、解码表、读取/恢复日志和原文件；详见 [离线重建与数据索引](离线重建与数据索引.md)。正常复现本包无需重新连接相机，也无需再进入维修模式。

## 5. 刷机操作路线

1. 下载仓库中的 `firmware/Z6II_C1.70_RAW_only/Z6_2_0170.bin`，先按 `SHA256SUMS.txt` 核对 SHA-256。
2. 不要改文件名；放在已由相机格式化的存储卡根目录，文件名保持 `Z6_2_0170.bin`。
3. 将存储卡装入当前指定为主插槽的卡槽。
4. 使用充足电量的电池，或按 Nikon 官方说明准备兼容的稳定供电。官方页面通常要求电池充满；没有必要把某个未经官方公布的百分比当成固定门槛。
5. 刷机前断开相机与电脑的 USB 连接。实机操作中，USB 连接时更新菜单只显示“完成”和“删除更新文件”；拔下 USB 后更新入口恢复可用。
6. 在相机菜单进入“设置菜单 → 固件版本 → 更新”，选择卡上的 `Z6_2_0170.bin`，按屏幕提示开始。
7. 更新过程中不要关机、拔电池、拔卡或重新连接 USB；等待完成，按屏幕提示关机并重新开机。
8. 开机后回到“固件版本”确认仍显示 C1.70，再检查相机的 HDMI 相关菜单。

本机实测记录：用户的 Z6 II 为 C1.70，使用此 RAW-only 文件完成刷入，反馈刷入后没有异常。该结果是单台机身的实测记录，不能替代每台设备的备份和风险判断。

## 6. 刷后检查 RAW

RAW 相关选项通常位于：

`设置菜单 → HDMI → 高级 → RAW output options`

启用后可检查 `RAW output`、`RAW output mode`、`RAW output type` 等项目。RAW 是 12-bit HDMI 外接录制流程，不是机内 N-RAW；官方指南中的 Type A 对应 Ninja V，Type B 对应 Video Assist 12G。设置、输出模式和兼容性按官方 RAW 指南核对。菜单出现本身不能证明实际 RAW 输出成功，应再用兼容录机识别、开始录制并回放样片。

## 7. 版本号、同版本重刷和限制

- 文件内版本字段保持 C1.70，没有把版本伪装成 1.60、1.61 或其他版本。
- 本次实机结果表明这台 C1.70 机身接受了同版本文件并完成更新；不能据此保证所有地区版本、维修状态或未来固件都允许同版本重刷。
- 本次已分析或观察到的条件包括包解析、摘要、机型、USB 状态和电量；文件名按官方升级流程保持原值。包内版本没有抬高，完整版本策略没有穷举验证。包解析、摘要比较等原始升级代码没有打补丁。
- 这不是 Nikon 官方发布物。若升级界面拒绝文件，不要通过反复断电强行推进。
